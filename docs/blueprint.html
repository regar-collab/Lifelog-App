0项目历程：从 0 到上线

这次实际走过的每一步 —— 做了什么、产出什么、在哪儿卡住过

STEP 0 环境搭建 起点：机器上什么都没有

起点很干净：只有 JDK 17，Flutter 和 Android SDK 都没装。

  • Flutter 3.47.7 → <开发目录>\flutter（1.93GB，走 storage.flutter-io.cn 镜像）
  • Android commandline-tools → <开发目录>\android-sdk
  • sdkmanager 装 platforms 35 / 36 / 37 + build-tools + platform-tools
  • Gradle 缓存也隔离到 开发盘 → <开发目录>\gradle-home（不占 C 盘）
  • 全套国内镜像：pub / flutter / Gradle 走腾讯云 / maven 走阿里云
产出：flutter doctor 全绿（只剩 Visual Studio 那项，做安卓用不到）
踩坑：Android SDK 37 官方包把 ApiLevel 写成了浮点数 37.0，AGP 解析不出整数、找不到目标。改成 37 才通。
STEP 1 项目地基 阶段 0
  • flutter create 生成项目，包名 com.simple.lifelog，只建 Android 平台
  • 装依赖：Riverpod 3.4.3 / Drift 2.35.2 / go_router 18 / Dio 5 …
  • 建 6 张表 + 索引，配好 Drift 迁移框架
  • 四 Tab 外壳（各自保留导航栈）+ 设置页（DeepSeek Key 输入 + 连通性测试）
产出：App 装进手机能跑，四个 Tab 能切，设置页能测通 DeepSeek
踩坑：permission_handler 13.x 要求 compileSdk 37，而 AGP 9.1.0 官方只支持到 36 —— 降级到 12.x 解决。
STEP 2 模块 1 · 收集箱 文字 / 图片 / 分享
  • InboxDao + Repository + MediaStorage（图片落盘到应用私有目录）
  • 列表页 + 「记一笔」页
  • receive_sharing_intent 接收系统分享 —— 冷启动和热启动两条路径都要处理
产出：文字、图片、从微信分享进来的内容都能存住并落库
踩坑：riverpod_generator 解析不了 Drift 生成的纯行类（抛 InvalidTypeException）→ 涉及 Drift 行类的 Provider 全部改成手写。
STEP 3 模块 2 · AI 整理 DeepSeek
  • DeepSeekService：纯文本调用 + 多模态（图片转 base64）
  • prompt 设计：注入当前时间、要求 JSON 输出、要求提炼和拆分
  • 两阶段流程：先生成草案弹窗给用户确认，确认后才写日程表
  • 用 ai_runs 表记录每次整理的原始返回，方便排查
产出：真机跑通 —— 模型返回的 JSON 被正确解析、写入 schedules 表、收集箱条目状态跟着流转
踩坑：模型返回可能带代码围栏、字段偶有缺失 → 解析器写成宽容模式，缺字段不崩。
STEP 4 需求迭代（三处改动） 数据库迁移 v1 → v2

第一版跑通后提了三件事，都动了数据库：

  • 条目变更历史 —— 像聊天记录一样，能看到每次改了什么（新增 inbox_item_revisions 表）
  • 模型统一 —— 原来按有无图片切换模型，改成全部走 deepseek-flash
  • 条目级整理控制 —— 三个点菜单加「重新整理」和「不再整理」（新增 organize_policy 字段）
产出：迁移保住老数据；编辑已整理的条目会自动退回待整理（堵上「改了却永远不会被重新整理」的漏洞）
踩坑：写迁移时忘了给老数据补 created 历史记录，点进去历史是空的。在 onUpgrade 里补了一条 INSERT ... SELECT。
STEP 5 模块 3 · 日程表 周视图
  • 周视图：左侧时间轴固定、右侧 7 列横向滑动，表头与网格滚动同步
  • 日程气泡按真实时刻定位、按持续时长决定高度，不是课表那种等高格子
  • 时间重叠的日程用贪心算法并排摆开
  • 双击气泡就地展开，露出这条日程来源的收集箱原文
产出：周视图正常渲染：今天高亮、当前时刻红线、双击展开来源都工作
踩坑：const [] 是只读列表，sort() 直接抛 Unsupported operation 崩掉整列。改成返回 <T>[]。
STEP 6 模块 4 · 定位轨迹 GPS + 保活
  • 坐标转换：WGS84 → GCJ-02（实测偏移 570 米，不转轨迹就跑到隔壁街去了）
  • geolocator 采集 + 批量落库（攒 5 个点写一次）
  • 前台服务保活：foregroundServiceType=location，锁屏也能继续记录
  • 三档精度可选（省电 50 米 / 平衡 15 米 / 高精度 10 米），设置页切换
  • 后台定位权限（Android 11+ 必须单独申请）+ 保活自检页
产出：真机验证 —— 会话正常创建结算、坐标两套都存、App 退后台 40 秒后进程和服务都还活着
踩坑：亲眼看到 App 一退后台就被系统限制、位置流断掉 —— 这正是必须上前台服务的原因。另外 FlutterForegroundTask.init() 返回 void 不是 Future，await 它会编译报错。
STEP 7 高德地图 + 计步 收尾
  • 申请高德 Android Key（绑定「包名 + 签名 SHA1」）
  • 自封装 PlatformView：约 300 行 Kotlin 包一层高德原生 SDK，只做「显示地图 / 画轨迹线 / 移动镜头」
  • 计步：读硬件计步芯片（微信运动同源），处理「开机以来总数」的基线问题
产出：地图正常渲染、能识别所在位置；计步验证通过（隔夜补算逻辑实测正确）
踩坑：高德 SDK 8.1.0+ 必须先调 updatePrivacyShow + updatePrivacyAgree，否则地图只显示灰色网格而且不报错，极难排查。
STEP 8 优化与开源 准备上传
  • 敏感信息清理：高德 Key 从硬编码改成从 local.properties 注入（该文件已 gitignore）
  • 补齐 .gitignore：local.properties / key.properties / *.jks / *.keystore
  • 补 README、架构文档、这份蓝图
  • 排除体积：build/ 2.4G、.dart_tool/ 240M 都不进仓库
产出：复制后的项目 pub get + analyze 零问题；全项目扫描敏感信息 0 命中
踩坑：换成正式签名后 SHA1 会变，高德 Key 需要重新申请一个。

2架构分层

数据从上往下流，两层之间有严格的规矩：UI 只跟 Provider 说话，业务规则一律写在 Repository

presentation 页面与组件，只负责画界面和接手势 features/*/presentation/
↓ref.watch / ref.read
application Provider / Notifier，状态编排与生命周期管理 features/*/application/
↓方法调用
data Repository —— 业务规则都在这层（例：改过的条目自动退回待整理） features/*/data/
↓数据访问 / 外部调用
db  +  services DAO 只管 SQL、不含业务；Service 封装外部依赖 data/db/daos/   data/services/
↓
平台层 SQLite  │  DeepSeek API  │  高德 SDK  │  GPS / 计步传感器  │  前台服务 Android
两条硬规矩： ① 页面不直接碰 Repository，更不碰 DAO —— 全部通过 Provider； ② 业务规则只写在 Repository 层，这样 UI 和 DAO 都不需要知道它。

三个关键设计： ① 轨迹点同时存两套坐标——WGS84 是真值（导出/换地图用），GCJ-02 给高德底图用，国内两者差 500+ 米； ② daily_steps 存传感器原始值，因为芯片只报「开机以来总数」，重启会清零； ③ schedules.source_item_ids 是 JSON 数组——一条日程可能来自多条笔记，一个条目也能拆出多条日程。

4四条核心流程

每个模块从用户操作到数据落库的完整链路

① 收集箱 · 记一笔 模块 1
记一笔 → 文字？ → 图片？复制进应用私有目录 → 写库 + 记 created 历史 → 列表自动刷新
另一入口 系统分享菜单 → ShareIntentService冷启动 + 热启动都要处理 → 落到同一个 Repository
② 编辑条目 · 自动回流 关键规则
改文字 / 换图 / 删图 → 内容真变了？没变就返回，不写库 → 写了 edited 历史 → 原来是「已整理」？ → 退回「待整理」
为什么必须回流：整理过 → 状态变 processed → 你改了内容 → 如果没有回流，这条再也不会被重新整理，改动等于白改。
③ AI 整理 · 两阶段 模块 2 刻意分开
取 pending 条目 → 写 ai_runsrunning → 组装 prompt注入当前时间
要求提炼 + 拆分 → 有条目带图？是 → base64 走视觉模型 → 调 DeepSeekjson 模式 → 解析出草案ai_runs = success
第二阶段 底部弹窗预览默认全选，可取消 → 点「写入日程」 → 批量插 schedules带 ai_run_id + 溯源 → 条目转 processed
为什么分两阶段：模型会抽风。草案先给用户看，确认之前绝不写进日程表。
④ 轨迹采集 · 全天记录 模块 4
开始记录 → ① 定位权限 → ② 后台定位Android 11+ 单独申请 → ③ 通知权限 → ④ 关电池优化 → 启前台服务type = location
建会话 recording → 订阅位置流精度和间距由设置档位决定 → WGS84 → GCJ-02两套坐标都存 → 攒 5 个点批量写库

省电档

  • GPS 精度 low
  • 移动 50 米采一个点

平衡档（默认）

  • GPS 精度 medium
  • 移动 15 米采一个点

高精度档

  • GPS 精度 high
  • 移动 10 米采一个点
前台服务为什么是命门：没有它，App 一退到后台就被系统限制，位置流直接断掉。 有了它 + foregroundServiceType=location，锁屏也能继续记录， 通知栏常驻显示「已记录 X 公里 · N 个点」。
⑤ 计步 · 和轨迹完全独立 模块 4 附加
读硬件计步芯片 → 今日步数= 当前值 − 上次记录的值 → 距上次 < 12h用上次的值当基线，能补隔夜步数
隔太久 从 0 开始计宁可少算，不虚高
重启过 传感器值倒退 → 重设基线

计步

  • 硬件：计步芯片（协处理器）
  • 耗电：< 1%
  • 需要前台服务：否
  • 需要定位权限：否
  • 数据：步数

轨迹

  • 硬件：GPS 芯片
  • 耗电：5 ~ 15%
  • 需要前台服务：是
  • 需要定位权限：是
  • 数据：经纬度序列

为什么微信运动省电

  • 它只用计步芯片，从不碰 GPS
  • 所以它只有步数，没有轨迹
  • 要轨迹就必须上 GPS，耗电躲不掉

6踩过的坑（备查）

换机器重装环境时，这些坑会原样再来一遍

坑现象解决
Android SDK 37 元数据 bug 报找不到 android-37 官方包把 ApiLevel 写成了浮点 37.0，改成整数 37
AGP 不支持 compileSdk 37 构建直接中断 gradle.properties 加 android.suppressUnsupportedCompileSdk=37
riverpod_generator 解析不了 Drift 行类 InvalidTypeException 涉及 Drift 行类的 Provider 全部改手写
const [] 不可变 Unsupported operation 崩溃 返回 <T>[] 而不是 const []
高德 SDK 不显示地图 只有灰色网格，且不报错 必须先调 updatePrivacyShow + updatePrivacyAgree
高德坐标偏移 轨迹整体偏 570 米 WGS84 → GCJ-02 转换
App 退后台轨迹断 位置流停止 前台服务 + foregroundServiceType=location
验证方法本身出错 误判「文字没渲染」 先确认元素完整可见，再用像素统计做佐证

7已知限制

第一版刻意没做的取舍

计步在 App 未打开时不计

  • 芯片只报「开机以来总数」，没有「今天从 0 开始」的概念
  • 重新打开 App 时会自动补上这段
  • 建议每天打开一次 App

AI 整理的 prompt 效果依赖模型

  • 「提炼」和「拆分」两条指令模型不一定 100% 遵守
  • 需要实际跑几次看效果，再调 prompt

轨迹会话不会自动跨天切分

  • 目前一次「开始/停止」算一段
  • 全天记录需要每天点一次

pedometer 插件用了旧式 Kotlin 配置

  • 现在只是构建警告
  • 未来 Flutter 版本会变成构建失败
  • 届时需升级插件或自封装
